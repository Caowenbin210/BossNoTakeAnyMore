# 《老板，真塞不下了！》C# / Unity 代码规范

版本：0.1 · 日期：2026-11-03 · 适用环境：Unity 2022.3 / C#

本文是本项目后续新增和修改代码的默认标准。目标是通过面向对象设计，让职责明确、状态可靠、规则可验证，并保持小型游戏应有的开发效率。标注“必须”“禁止”的条目为代码审查要求；“建议”允许根据具体情况调整，并说明理由。

关联：[游戏设计总纲](GameDesign.md) · [操作与规则说明](InteractionRules.md) · [前 3 关设计](LevelDesign.md)。本文规定如何实现，不改变玩法定义。

## 1. 面向对象基本原则

### 1.1 单一职责

- 每个类必须有一个清晰的主要职责，能用一句话说明。
- 棋盘状态、放置判定、输入处理、界面显示、存档和广告必须分离。
- 禁止让一个 `GameManager` 同时处理触摸、格子计算、货物动画、结算、音频和广告。
- 文件长度不是拆类的唯一依据；当一个类同时因不同业务原因变化时，应拆分职责。
- 不强制“每个类少于多少行”或“每个方法少于多少行”，但方法必须围绕一个明确操作，避免难以追踪的嵌套和副作用。

### 1.2 封装与状态所有权

- 可变字段默认 `private`，禁止通过公开字段让外部直接修改业务状态。
- 对外通过语义明确的方法操作，例如 `TryPlace`、`TryRotate`、`RemoveCargo`，不要暴露任意修改占格的方法。
- 只读查询使用属性、查询方法或只读快照；不能把内部可变集合直接返回给调用方。
- `IReadOnlyList<T>` 等接口不自动保证底层不可变，必须控制集合引用与元素本身的可变性。
- 每份状态必须有唯一权威来源。棋盘占用由棋盘模型维护，不能同时由货物视图和控制器各维护一份独立真值。
- 禁止用视图的 `Transform.position` 或动画进度反推正式占格。

### 1.3 组合优先于继承

- 优先通过对象组合组织能力，例如关卡控制器持有棋盘模型与放置服务。
- 继承必须表达稳定的“是一种”关系，禁止仅为复用几个方法建立继承层级。
- 不预先建立 `BaseManager`、`BaseService`、`BaseEntity` 等缺少明确行为约束的通用基类。
- 值类型适合坐标、朝向和结果等小型值；不为了“面向对象”把所有值都包装成可变类。

### 1.4 接口与多态

- 在确有替换边界时使用接口，例如模拟与真实广告服务共享 `IRewardedAdService`。
- 禁止为了形式上的统一，给每个类机械添加一个接口。
- 尚不存在的特殊规则不提前扩成庞大规则框架。第二种规则出现且确有复用需求时，再提取共同契约。
- 接口描述调用者所需能力，不暴露第三方 SDK 的具体类型或完整 API。

## 2. 模块划分与依赖方向

推荐目录：

```text
Assets/_Game/
  Scripts/
    Core/          坐标、形状、运行状态、放置与旋转规则
    Data/          ScriptableObject 配置及转换、配置校验
    Gameplay/      输入、拖动事务、关卡流程与完成判定编排
    UI/            视图、按钮、弹窗、界面动画
    Services/      音频、存档、广告等外部能力
    Bootstrap/     创建对象、绑定引用、连接各模块
    Editor/        仅编辑器工具
  Tests/
    EditMode/
    PlayMode/
```

| 模块 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| Core | .NET 基础能力、Core 内部类型 | UnityEngine、UnityEditor、UI、SDK、文件或网络服务 |
| Data | Core、Unity 配置类型 | UI、Gameplay、广告 SDK |
| Gameplay | Core、必要的 Unity 输入与生命周期、服务契约 | 具体广告 SDK、Editor |
| UI | 展示所需 Core 值与 Gameplay 对外操作、Unity UI | 直接改写棋盘内部数据、具体广告 SDK |
| Services 实现 | 自身契约、必要的平台或 SDK 类型 | UI、关卡视图、Editor |
| Bootstrap | 上述运行时模块 | Editor |
| Editor | 配置与所需运行时类型、UnityEditor | 被运行时模块反向引用 |

服务契约与服务实现可以先用目录、命名空间分隔；建立程序集时，契约放独立程序集，避免 Gameplay 被迫引用广告 SDK。UI 将输入意图交给 Gameplay，Gameplay 通过结果或事件通知 UI，不能反向引用具体 UI 类。

原型不强制为每个目录建立 `.asmdef`。需要测试程序集、隔离 SDK 或控制编译依赖时再划分，保证无循环引用。命名空间不能代替程序集依赖检查。

## 3. 核心对象职责

| 对象 | 主要职责 | 不应负责 |
| --- | --- | --- |
| `CargoDefinition` | 货物基础形状、标识与展示配置 | 当前摆放位置、选中状态 |
| `LevelDefinition` | 车厢、货物清单、初始朝向和参考解 | 修改运行中的棋盘 |
| `CargoState` | 单件货物的运行时 ID、区域、位置和朝向 | 操作视图与播放音效 |
| `BoardState` | 维护权威布局与占格不变量 | 响应触摸、处理广告 |
| `PlacementValidator` | 对候选放置执行无副作用的合法性检查 | 自动移动货物、弹出提示 |
| `DragController` | 处理指针与拖动事务，生成操作意图 | 复制一套放置规则 |
| `LevelController` | 协调加载、状态转换、提交、重置和完成 | 直接实现所有服务和动画 |
| 视图类 | 显示状态、预览和反馈，转发 UI 输入 | 自行决定业务是否合法 |
| 服务类 | 执行音频、持久化、广告等特定能力 | 决定关卡胜负 |

对象名称可随实际实现调整，但职责边界必须保留。纯规则对象使用普通 C# 类，不继承 `MonoBehaviour`；配置资产使用 `ScriptableObject`；仅需要生命周期、场景引用或组件能力的对象继承 `MonoBehaviour`。

## 4. 数据和不变量

- 配置是模板，运行状态是实例。禁止在游玩过程中修改配置资产来保存位置或工资。
- 开关时从配置创建独立状态，重置时恢复初始配置，不复用上次未清理的状态。
- 货物实例使用关卡内唯一 ID，相同形状也不能共享实例 ID。
- 业务坐标使用整数值类型，例如 `GridPosition`；屏幕坐标、世界坐标和格子坐标必须通过明确的转换边界区分。
- 朝向建议使用四向枚举或受限值类型，不在各处散布任意角度浮点数。
- 形状旋转、归一化和候选占格计算只有一个实现来源，预览和提交共享它。
- 参考解必须经过实际放置规则校验，不能作为唯一允许答案。
- 禁止将不存在、重复或非法货物数据静默替换成默认数据继续运行。

核心不变量：同一格最多被一件货物正式占用；每件货物只有一个所属区域；正式位置与占格一致；拖动事务最多一个；每次关卡运行最多完成一次。

## 5. 事务与状态机

- 拖动必须保存完整起点快照。临时释放原占格后，成功则提交，取消、失焦或暂停则完整回滚。
- 正式布局的修改必须是原子的：先计算和验证，再一次性更新位置与占格；不允许失败后留下部分更新。
- 预览不得改写正式布局。若为拖动临时释放占格，必须明确处于事务内，不进行通关检查。
- 关卡流程建议使用显式状态，例如 `Playing`、`Paused`、`Completing`、`Completed`。状态名称可调整，允许的转换必须明确。
- 禁止用多个互相独立的布尔值拼凑可能冲突的流程，例如同时 `isPlaying=true` 与 `isCompleted=true`。
- 进入完成状态时先封锁重复提交，再播放动画或通知结算。动画回调不能决定规则是否成立。
- 切换关卡时创建新的运行标识，旧协程、异步任务或广告回调不得修改新关卡。

## 6. 命名与文件组织

- 类型、方法、属性、事件、枚举成员使用 `PascalCase`；接口使用 `I` 前缀。
- 私有字段使用 `_camelCase`；参数和局部变量使用 `camelCase`；常量使用 `PascalCase`。
- 命名空间以 `BossNoTakeAnyMore` 为根，例如 `BossNoTakeAnyMore.Core`。
- C# 文件名与主要类型一致，每个文件一个主要类型；简短且紧密相关的嵌套类型可以保留在同文件。
- 使用英文标识符，避免拼音、模糊缩写和 `Manager1`、`data2` 等无语义命名。循环索引 `i`、坐标 `x/y` 等局部惯例除外。
- 布尔值体现判断含义，例如 `IsPlaced`、`CanRotate`；`Try...` 方法表示预期可失败的尝试。
- 事件名表达已经发生的事实，例如 `PlacementCommitted`、`LevelCompleted`，不使用模糊的 `OnEvent`。
- Unity 消息方法保留标准名称。自定义事件处理方法可使用 `Handle...`，便于与事件本身区分。

## 7. C# 编写约定

- 缩进 4 个空格，不使用 Tab；大括号独占一行，条件与循环即使只有一行也保留大括号。
- 显式声明访问级别；字段默认 `private`，不需要继承的具体业务类建议 `sealed`。
- 能在构造后保持不变的字段使用 `readonly`。Unity 序列化字段不通过 `readonly` 期待 Inspector 支持。
- `var` 仅用于右侧类型清晰的场景；表达式不明确时写出类型。
- 提前返回处理无效条件，减少嵌套；不使用难读的多层三元表达式。
- 避免魔法数字。业务阈值使用命名常量或配置；简单的四向旋转等局部数学常量不必全部做成资产。
- 注释优先说明原因、不变量和生命周期，不逐行翻译代码。复杂公共规则与服务契约使用 XML 注释。
- 不启用超出当前 Unity 编译器与目标平台能力的语法或库特性；纯数据示例也应遵守实际兼容环境。

```csharp
    {
        None,

        BlockedCell,
        Overlap
    }

    public sealed class PlacementValidator
    {
        // 只计算结果，不修改棋盘或候选货物。
        public bool CanPlace(
            BoardSnapshot board,
            PlacementCandidate candidate,
            out PlacementFailure failure)
        {
            // 此处省略实现，BoardSnapshot 与 PlacementCandidate 为契约示意。
            throw new System.NotImplementedException();
        }
    }
}
```

此代码仅说明命名与职责，不是可交付实现。生产代码不得遗留此类未实现分支或占位成功返回。

## 8. Unity 专项约定

- Inspector 引用使用 `[SerializeField] private` 字段，不为序列化而暴露 `public` 可变字段。
- 必需引用在初始化时验证，缺失时清楚报错并停止对应功能；不每帧查找补救。
- 不把 `FindObjectOfType`、`GameObject.Find` 或单例搜索作为常规依赖获取方式。优先 Inspector 绑定和 Bootstrap 显式注入。
- 普通类通过构造函数传入依赖；`MonoBehaviour` 通过显式初始化或序列化引用，不编写带参数构造函数。
- 不依赖不同对象 `Awake` 的隐含执行顺序，跨对象初始化由 Bootstrap 协调。
- 禁止默认使用全局可变单例、静态棋盘和静态当前关卡。静态纯函数、常量允许使用。
- 事件订阅与取消订阅必须配对。根据对象生命周期选择启用期或整个存活期，不盲目统一放到某个回调。
- 禁用或销毁时停止自己拥有的任务、协程和拖动；对象池复用前清理状态。
- Unity 对象是否已销毁使用 Unity 的空值语义判断，不能假定 `?.`、`??` 能识别已销毁对象。
- 编辑器代码放 `Editor` 目录或 Editor 专用程序集，运行时构建不得引用 `UnityEditor`。
- 序列化字段改名且需保留资源数据时使用 `FormerlySerializedAs`，修改后检查场景和预制体引用。
- 使用与时间缩放无关的时间驱动暂停菜单等需要继续播放的 UI 动画；玩法计时和界面计时必须区分。

## 9. 事件、异步与服务边界

- 简单调用优先直接方法；一对多通知使用局部事件。不建立缺少必要性的全局字符串事件总线。
- 事件由状态所有者发布，发布前先完成状态更新。处理方应防止重入或重复请求。
- 异步操作必须明确所有者、取消策略、错误处理与过期结果判定。避免无法追踪的 fire-and-forget 调用。
- 除事件签名等必要入口外不使用 `async void`；必要入口内部仍须捕获异常或转交可观察任务。
- 第三方回调若可能来自后台线程，先切回 Unity 主线程，再操作 Unity 对象。
- SDK 的返回类型不穿透服务边界，转换为本项目的明确结果，如成功、取消、未加载或失败。
- 广告关闭不等于奖励成功；只有服务确认有效奖励后，业务才可尝试发奖。
- 奖励使用本次请求或结算标识做幂等检查；重复回调不重复奖励，迟到回调不能奖励错误关卡。
- 原型模拟服务须明确标识，在正式构建中不得误作真实广告服务。

## 10. 错误处理与日志

- 越界、重叠、广告未加载等预期结果用返回值或结果类型表达，不用异常控制正常流程。
- 配置损坏、缺失依赖等程序错误应快速暴露，提供关卡 ID、货物 ID 等必要上下文。
- 禁止空 `catch`、捕获后继续假装成功，或只打印没有上下文的“出错了”。
- 日志不记录密码、签名信息、广告密钥和个人敏感数据。
- 拖动每帧不打印正常日志。开发诊断日志可以受编译条件或开关控制，真实错误不能全部被隐藏。

## 11. 性能与资源管理

- 优先保证正确性，再根据真机表现优化；不预先引入复杂缓存和对象池。
- 拖动与预览等高频路径避免重复创建集合、闭包、字符串和 LINQ 链；低频配置处理可使用清晰的标准写法。
- 缓存重复使用的组件引用，不在 `Update` 中反复查找。
- 没有逐帧职责的对象不要添加空 `Update`。界面刷新由状态变化驱动，拖动中的预览按输入变化更新。
- 明确运行时创建的材质、纹理、音频和订阅的释放责任，避免不断创建独立材质实例。
- 只有实测有收益时才引入对象池；池化货物必须重置选中、预览、事务相关状态和事件绑定。

## 12. 验证与提交标准

规则测试优先覆盖：旋转四次恢复、非矩形占格、四边越界、禁用格、自己占格排除、非法提交不改状态、拖动回滚、全部合法解通关和完成只触发一次。新增规则必须补充对应有意义的验证，不为简单包装方法机械写测试。

交互人工检查覆盖：鼠标、安卓触摸、多指忽略、失焦、暂停、重置、快速重复点击、不同屏幕安全区域。纯 Python 关卡求解验证不能代替 Unity 的规则和输入验证。

每次交付检查：

- Unity 无新增编译错误；必要的 EditMode / PlayMode 测试通过。
- 改动未破坏本次涉及的关卡、预制体和序列化引用。
- 行为变化同步更新规则或设计文档，未完成项明确列出，不用成功占位隐藏。
- 新增资源带 `.meta`，不提交 `Library`、`Temp`、构建缓存或私钥。
- 提交围绕一个明确目的，说明修改原因和验证结果；不顺手重构无关模块。
- 当前无法执行的检查如实说明，不把静态检查写成已完成真机测试。

## 13. 审查重点

审查时先问：状态由谁拥有？业务变化是否通过唯一入口？取消后能否恢复？预览与正式判定是否一致？旧回调会不会影响新关卡？

若一个新抽象不能减少当前的重复、隔离真实外部依赖或保护明确不变量，先保留简单实现。面向对象规范用于控制变化和错误，不以类、接口或设计模式的数量作为质量指标。
